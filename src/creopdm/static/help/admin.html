Looking for everyday file work (checkout, check-in, Revise as a user)? Open the regular CreoPDM help. Every page shows only the tiles and buttons the signed-in user has permission for.

How to administrate CreoPDM

Administration covers who can sign in, what each person can do, which products they can open, what state each product is in, and the server tools that keep it healthy. Every page below says what its fields do, what is checked, and what cannot be undone. Start at Administration in the top bar.

Quick start

The Administration page is a set of tiles. A tile appears only when your role has the matching permission, so two administrators can see different pages.

TileWhat is behind it
UsersAdd and edit accounts, assign a role, set status.
RolesCreate roles and choose what each can do (products, files, administration).
Manage productsProducts, Product Membership, Copy, Promote, Lifecycle states, then Delete, Compact and Rebuild.
UtilitiesEmail all users, Audit log, Health and Logs.
System SettingsServer-wide options: Open Creo models, Vault, file types, the local agent, Database, Email, AI, Availability.

A good order for a new server

  1. System Settings: check the Vault folder, Network port and, if you use Postgres, the Database URL (it takes effect at the next restart). Set up Email so password reset and notifications work.
  2. Roles: review the four starter roles and adjust them (Roles & permissions).
  3. Lifecycle states: confirm what each product state allows (Lifecycle states).
  4. Users: create accounts, then give each person product access under Product Membership — new users start with no product access.
  5. Products: create or copy the products people will work in.
Two layers decide what a person can do. The role says what the person may do at all; the product’s lifecycle state says what is allowed on that product right now. A button appears only when both agree — “state ∩ role”. Permissions are also checked on the server, not just by hiding buttons.
Always keep at least one active user who has every administration permission. CreoPDM refuses to remove the last one.

Users

Administration → Users lists every account with its name, username, role, status and product access. Click a name to edit that user, or a role name to edit that role.

Adding a user

FieldRules
Display nameShown in the top bar and on history rows.
Username2–64 characters: letters, numbers or underscore only, no spaces. Sign-in is not case-sensitive.
EmailMust look like name@example.com (a real ending such as .com or .ca). Used for watch emails and password reset.
RoleYou can only assign a role with fewer permissions than your own — not your own role and not a higher one. New users start as Engineer.
StatusACTIVE can sign in. DISABLED cannot; their history and audit entries stay.
Password / ConfirmInitial password, at least 8 characters. The user must change it at first sign-in.

Rules to know

  • New users get no product access. Grant All products or a list under Product Membership (needs the products.assign permission). Until then they sign in and see nothing to open.
  • Creating a user, or setting or resetting a password later, needs users.password. Changing a role needs roles.assign. users.manage alone cannot do either.
  • You cannot change your own role, disable yourself, or change your own status. Another administrator has to.
  • Only a full administrator can edit their own account or other administrators’ accounts.
  • To reset a password, edit the user and enter a new password (at least 8 characters, they must change it at next sign-in); leave it blank to keep the current one.

Roles & permissions

Administration → Roles lists each role with its description, how many users have it and its permissions. Assign roles to users on the Users page.

Starter roles

  • Administrator — everything. PDM Manager — engineering data without full server administration. Engineer — everyday authoring (including Revise). Viewer — read-only access to assigned products.
  • Baselines have two permissions: baselines.view (all starter roles) and baselines.create (Administrator, PDM Manager, Engineer). A baseline freezes the exact version of every file in a product; while one exists, Compact, Rebuild file list and removing its files from the product are refused, and deleting the product deletes its baselines.
  • They are only a starting point: edit them or add your own. A role is saved by its permission ticks, grouped on the role page.

Rules to know

  • At least one active user must keep full administration: users.manage, users.password, roles.assign, roles.manage, products.assign, products.manage, settings.manage, email.manage and every utilities.* key. This stops administrators locking themselves out.
  • On your own role, the name, description and administration permissions are locked. You can still change Products and Files permissions. Ask another administrator for the rest.
  • A role that is assigned to users cannot be deleted — reassign them first. You cannot delete the role assigned to you.
  • A role that can see a file but cannot check it out simply never gets the checkout buttons.

Products

Administration → Manage products is the hub for everything about a product; each tile is its own page. Products lists every product on this server (including Archived) with name, created date, number, state, vault folder and description.

Add a product

  1. Choose Add product and enter a Name (required, and unique across all products, even inactive or Archived ones).
  2. Optional Number and Description. The sidebar shows the number under the name only when one is set.
  3. The Vault/Workspace name is the folder under the vaults directory. Use hash is ticked by default: a unique id is filled in and locked.
  4. Untick Use hash to type your own name — no spaces, and it cannot match another product’s vault name.
  5. Pick the starting Lifecycle state (default In Work) and choose Create product.
  • Edit product changes the name, number and description. The vault folder is fixed at creation and cannot be changed. The lifecycle is changed under Promote Products.
  • Copy Products: pick a product, then Copy. It makes a new product (new id, new vault) from the original’s current vault files, the same way Add does: each file starts at A.1, In Work, not checked out, with a clean Git history of just that first Add. You can add an initial History comment. The original is not changed.

Product Membership

Decides who can open which products. There are two ways in, both under Manage products → Product Membership:

By product

Open a product, then tick which restricted users are members and choose Save members. Users with All products already see it.

By user

Open a user, then tick All products, or untick it and multi-select products (Ctrl/Cmd-click). Save membership.

  • The summary table shows, per product, Members (everyone who can open it: restricted members plus All-products users) and Restricted (users without All products who are explicitly on it).
  • With All products off and nothing selected, the user cannot browse any product.
  • Membership never gives more than the role allows; it only limits which products are visible.

Lifecycle states

Manage products → Lifecycle states defines the product states and which operations each state allows. Role permissions still apply on top (state ∩ role). New products default to In Work.

The permission matrix

Each row is a state with an Order, a State label and a Description. Each column is an operation, ticked when the state allows it:

ColumnWhat it controls
Read / ViewSeeing the product and its files.
Download / Export / OpenOpening files in Creo, downloading and exporting.
Check Out / Undo CheckoutChecking out, and releasing your own or another user’s checkout.
Check In / Add / UploadCheck-in, adding files, uploads.
Delete / Remove (vault)Removing files from the vault.
Edit MetadataCollect, rebuild metadata, AI snapshots.
Revise (new revision)Offering Revise… for Released files.
Rename productChanging the product’s name.
View History / AuditHistory tabs and audit views.

Default states

  • Pre-Work and In Work are editable. In Review, Approved and Released are frozen. Under Change is editable again. Obsolete, Archived and Locked are frozen (Locked also blocks download).
  • Revise is allowed in In Work and Under Change, and off in Pre-Work and every frozen state.
  • Archived products are hidden from the normal Files list; administrators still see them in Manage products.

Buttons on the page

  • Save applies the matrix to everyone at once. Reset to defaults puts the built-in matrix back.
  • Add lifecycle state: enter a Name (and an optional description). CreoPDM makes a state key from it (for example PROTO_A); its permissions start like In Review — view, download and history only — so you tick what it should allow.
  • States you add are marked custom and can be deleted; the built-in states stay.

Promote Products

Manage products → Promote Products changes one product’s lifecycle state. Pick the Product and the new Lifecycle state, choose Change state, read the summary of what the new state allows, and confirm with your password. Name, number and description stay as they are.

Releasing

Moving a product to Released also marks its files Released (files already Obsolete stay Obsolete). That is what makes Revise available later.

Release baseline

When you promote to Released, Create a release baseline is ticked by default. It records release R1, R2, … and a baseline with the exact version of every released file, so that release can be rebuilt later (Files → Baselines → Download baseline…). It is strict: if a required dependency has no checked-in version, Where Used has not been built for a product with assemblies or drawings, or released content is missing, the promotion is refused with the reason and nothing changes. Untick the box to release without a baseline. Also tag the repository (ticked by default) adds the Git tag release/R1, release/R2, … on the release’s commit, so the release can be found in the vault repository. If the tag cannot be created the release still stands and you can Retry tag from the baseline.

Checked-out files

Promoting to Released, In Review or Approved is refused while any file is checked out; the message names the files and who holds them. Check them in or undo the checkout first.

Going back

Moving a product back to Under Change or In Work leaves its files Released. Each one needs a Revise before it can be edited.

Undo a release

When you promote a product that has Released files to In Work or Pre-Work, a box appears: Also set the N Released files back to In Work (undo the release). Tick it to unlock them without Revise, for example after a release by mistake. Files already In Work are untouched; earlier Released revisions keep their state.

Promote is recorded in the Audit log as Product state changed, with how many files were released or set back to In Work. A product that is already in the chosen state is refused.

Revise (admin view)

Users start the next revision of a Released file with Revise… (A.3 → B.1). As administrator you control who and when:

  • Who: the objects.revise permission on the role.
  • When: the product’s state must allow Revise in the matrix (In Work and Under Change by default), the file must be Released, and nobody may have it checked out.
  • Reopening a released product for revision: promote it to Under Change. A product that is itself Released is frozen and does not offer Revise.
  • The Revise dialog needs a reason (up to 500 characters). The server picks the next revision letter (A → B → … Z → AA); it cannot be typed in. A retry after a lost answer returns the same new version.
A user says they cannot see Revise? Check in this order: the file reads Released · it is not checked out · their role has Revise · the product’s state allows Revise · the page was reloaded after a deploy.

Each revise appears in the Audit log as Revision created (A.3 → B.1, with the reason). The new revision keeps its own copy of the metadata; the released one is never changed, and baselines and product releases keep pointing at the version they used.

Baselines

Administration → Manage products → Baselines (the baselines.admin permission, Administrator by default) lists every baseline of every product. Engineers create, view, compare and download baselines from a product’s Baselines tab; this page is for looking after them.

  • The list: search by baseline, product or creator; filter by Type (Manual or Release) and Status (Finalized or Archived). The counts at the top include Integrity warnings and errors once you have run a check. A baseline name opens that product’s Baselines tab if your account can open products; an admin-only account sees the name as text and uses Check for details.
  • No Delete: a finalized baseline is immutable and protects the file versions it holds (they cannot be removed, compacted or rebuilt away while it exists). Deleting a product removes its baselines with it.
  • Archive / Restore: Archive shows a confirmation window that explains what happens and asks for your password (the same as other administration actions). An archived baseline is hidden from the product’s Baselines tab and its count (users can tick Show archived to see it), but it stays here, stays readable, comparable and downloadable, keeps its name reserved and keeps protecting its versions. Nothing is deleted. Both actions are written to the Audit log.
  • Check (one baseline) and Run integrity check (all, quick): verifies the member records, that every exact file is still in the vault, that the stored Git commit exists, and the optional Git tag. It only reports: it never repairs, changes membership or substitutes a newer version. Verify file hashes in the details also reads every file and checks its SHA-256 (slower).

Error

Missing or damaged content, a missing repository commit, or missing records. The message names the file and version. Restore the vault from a backup; the baseline itself is intact.

Warning

The optional Git tag was moved, deleted or never created. The baseline still points at its stored commit, which is the record.

Collaboration (comments)

Users discuss products, files, versions and baselines from Discussion tabs, with @mentions, pasted images, a resolve/reopen loop, toast pop-ups and a notification bell. Nothing needs to be turned on.

  • Permissions (Roles). Four keys in the Collaboration group: comments.view and comments.add (all starter roles), comments.resolve (Administrator, PDM Manager, Engineer: resolve or reopen any thread; the thread's author and anyone mentioned in it can always do so) and comments.admin (Administrator: delete anyone's comment). Change them per role in the matrix.
  • Who takes part is product access. The audience of a product is every active user with All products access plus those listed under Product Membership for it. Mentions, notifications, toasts and watcher e-mails are limited to that audience, and a mention or notification only reaches someone whose role has comments.view (a role without it cannot see comments); removing someone's access hides that product's notifications from them at once.
  • E-mail is optional. Toasts, the bell and the inbox always work. If System Settings → Email is on, mentioned and replied-to people with a usable address also get an e-mail, and watchers get Comment added. If it is off, nothing is sent and nothing is reported as an error. A failing mail never blocks a comment.
  • Images are stored in the database (included in backups): PNG, JPEG, GIF or WebP only (no SVG), re-encoded to strip metadata, at most 4 per comment and 5 MB each. Pictures never attached to a comment are discarded after 24 hours. Only people with access to the product can view them.
  • Audit log. Comment added / edited / deleted / resolved / reopened appear with who, product, file and version, an excerpt, the people mentioned and the number of images. The rows stay when a comment, a file or a product is deleted.
  • Clean-up. Removing a file deletes its comments; deleting a product deletes all of its comments, images and notifications (not the audit rows).

Delete, compact, rebuild

These three sit under Manage products, in red. Each needs its own Utilities permission, your password, and a tick on an “I understand…” box. Choose the product from a list (Archived and inactive products are included and marked).

Delete products

Deletes the product’s CreoPDM vault (working copies and Git history) and unregisters the product from the database. Works for Archived and locked products. Original CAD folders you imported from are not deleted. The product’s rows in the Audit log are kept.

Products with baselines. Baselines are permanent records, so nobody can delete such a product from the Files page — only an administrator, here. When you pick a product that has baselines or releases, a red warning names them and an extra box (“its baselines will be erased too”) must be ticked. They are then erased with the product, and the Audit log’s Product deleted row says how many.

Compact product vault history

Squashes one product’s vault to a single tip commit and runs Git cleanup so the bytes of removed files leave .git/objects. The tip files stay, but all older History versions of every file in that product are destroyed — Revert to those rows no longer works. Release every checkout first and make sure the vault is clean.

Rebuild product database

Repairs one product’s database rows without rewriting vault Git history. Choose one action:

  • Rebuild file list from vault Git tip — replaces the product’s file list from the vault. It also clears checkouts, Where Used and Creo metadata for the old rows. Every checkout must be released first.
  • Delete collected Creo metadata — clears identity, BOM and parameters only.
  • Delete and rebuild Where Used — clears the dependency links and re-indexes from the vault (the same as the product gear). Works when the product is locked or Archived (admin recovery).
Compacting and deleting cannot be undone from CreoPDM. Keep a copy of the vault folder first if you may need the history again.

System Settings

Administration → System Settings holds server options for this install. They are stored in the server settings, not in any product’s Git history. The page is a hub of tiles, each its own page; you see the tiles your permissions allow.

Email & notifications

System Settings → Email chooses how CreoPDM sends mail. Product Watch emails, password reset and Email all users all use it.

AI

System Settings → AI controls the optional Ask AI tools (Ask AI what changed on Modifications, Ask AI for comment at Check In).

  • Enable AI features — when off, those buttons are hidden, the Ollama compare API refuses requests and the fields below are disabled. The plain Computed differences on Modifications still work.
  • Ollama host URL — host name or IP plus port, with the scheme (for example http://127.0.0.1:11434 or http://michael-desktop:11434). The default Ollama port is 11434.
  • Refresh models asks the CreoPDM server first, then falls back to this browser if the server cannot reach Ollama — common when Ollama runs on a Creo PC and CreoPDM on another host. Then choose the Model.
  • Snapshot compare prompt — the system instructions for Ask AI what changed. CreoPDM appends plain-language OLD and NEW outlines after it (not raw JSON). When nothing changed, CreoPDM answers “Nothing changed between A.1 and A.2.” itself without calling Ollama. Paste, Save, then try again on Modifications.
  • The settings.ai permission is separate from general settings.

Utilities

Administration → Utilities holds the day-to-day server tools. Each tile needs its own permission. Compact, rebuild and delete live under Manage products, and Availability under System Settings.

Email all users

Sends one message per active user using the Email delivery settings. Addresses stay private (they are not in To or Cc). Enter a Subject and Message; the page shows how many active users with an email will receive it, and you tick I want to email all N active users before Send email to all users. Use it for downtime notices.

  • Audit log, Health and Logs are described below.

Health & Logs

Health

Utilities → Health re-runs its probes each time you choose Refresh. Look here first when the server is slow or something looks wrong.

SectionWhat it shows
System healthApplication and overall status (with the reason when degraded), server time, host, platform, Python, site availability, whether authentication is enabled, and the agent URL.
DatabaseA probe result, the dialect (SQLite or Postgres) and the URL.
GitThe Git executable and its version.
CPU and I/OA short sample at refresh: load, logical CPUs, load average, I/O wait (a Linux metric), disk read and write, and network receive and send (loopback excluded). They are information only and do not change the overall status.

Logs

Utilities → Logs lists the files in the server log folder and shows the end of the selected one (default creopdm.log); use Refresh for newer lines. When a page shows an “unexpected error”, the real cause is in the last lines here.

Audit log

Utilities → Audit log records what happened, who did it, from which client, and to which product and file. It is append-only: deleting a product keeps its rows (marked (deleted)).

Finding events

  • Filters: Search, Event (a type such as Check in/Check out), User, Product, Object, From date and To date. Apply filters or Clear.
  • Export CSV downloads the events that match the filters.
  • Each row shows the time, event, user, client, product, file, and a comment or summary. Events that touched many files show the first and “(+N more)”.

What is recorded

  • Check in / Check out, Object added or removed, Checkout cancelled or overridden (Force Undo).
  • Revision created (A.3 → B.1, with the reason) and Version restored (for example Restored A.1 as D.3).
  • Changes discarded when someone throws away unsaved vault changes.
  • Metadata collected: one row for each Collect metadata run, whether started by hand or automatically after an Add, with the counts (for example 936 files: 930 saved, 3 failed, 3 skipped in 2 min 5 s, marked cancelled if it was stopped). There is never one row per file, and Open and Check-in do not write one.
  • Where Used rebuilt: one row for each Where Used run, manual or automatic, in the name of whoever started it, with the links added, files scanned and time (marked cancelled or failed: reason otherwise).
  • Product state changed with “N files released” or “N files set back to In Work”; product created, copied, updated, deleted; vault compacted; database rebuilt.
  • Sign-in and sign-out, failed sign-in, password, role and membership changes, user created or disabled, and system-setting changes.

Troubleshooting

A delete or rebuild fails with “unexpected error”

Open Utilities → Logs, select creopdm.log and read the last lines — the real cause is there. Send the error text when asking for help.

A user signs in and sees no products

New users have no product access. Grant All products or a list under Product Membership, and check their role has products.view and objects.view.

A user cannot check out or check in

Check the product’s state in the Lifecycle matrix (Check Out and Check In columns) and the role’s permission. A Released file also cannot be checked out until it is revised.

A checkout is stuck

Use Force Undo Checkout (permission required) in a state that allows Check Out. In a frozen state, promote the product to Under Change or In Work first.

A file keeps reading Modified

Right-click it → Discard changes… (also on its row on the Modified tab). It restores the vault copy and, for a Newer local save, moves the local file to the Recycle Bin on that PC. No checkout may be held.

Promote is refused

Read the message: files are checked out (Released, In Review, Approved), or the product is already in that state. Check the files in or undo the checkouts, then try again.

Menus look old after an update

Reload the page; if a menu item is still missing, hard refresh (Ctrl+F5). The server serves its scripts fresh, but browsers cache some files.

Creo: Agent offline

The agent tray is not running on that PC. Collect metadata, Rebuild metadata and Open need it. See the user help for starting it; check the agent URL under System Settings → Local Creo agent.

Before you change something big

  1. Mark the site Unavailable (System Settings → Availability) and email users from Utilities.
  2. Make sure nothing is checked out (Checked out tab on each product).
  3. Check Utilities → Health for disk space and the database.
  4. For compact, delete or rebuild, keep a copy of the vault folder.
  5. Make the change, then turn Availability back on.
