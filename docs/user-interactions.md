# User interactions — what you do, what CreoPDM should do

Plain-language guide for **manual testing**. For each action: what you do, what the app **should** do, and what it **must not** do.

After you add, remove, or open something, the Files list should update **on its own** — you should not need a hard browser refresh (F5).

Test in Creo’s built-in browser when you can (Creo connection matters there). A normal browser is fine for most list/toolbar checks. On a **phone**, see [§14 Mobile browse](#14-mobile-browse).

## 1. Moving around the app

| You do | App should | App must not |
|--------|------------|--------------|
| Click **Help** in the top bar | Open `/help` in a named browser tab (`creopdm-help`) so CreoPDM stays in the original tab; later Help clicks reuse that help tab | Soft-nav Help into the Creo shell; open a new anonymous tab every click |
| Click around the signed-in app (product, folder breadcrumb, **Details** / History tab, double-click a file, Administration including Products/Product Membership/Email/Utilities, System Settings, account password) | Soft-nav the shell so Creo **stays Connected**; if Creo.JS is live, the pill shows **Connected** (not a stale Session offline) when **Set Working Directory** is shown; inside Creo’s embedded browser while Creo.JS is still linking, show a **Connecting to Creo…** overlay that blocks clicks until Connected (or ~15s), then clear it — never in Chrome/Edge and **never on Logout → sign-in** (`/login` / auth pages — do not block typing for ~15s); on a **fresh open** of Creo’s browser (close/reopen), promote **Connected** as soon as the bridge is live (do not wait on creopdm-agent `/health`), start `/creojs.js` after a short grace if Creo has not injected it yet, and poll the overlay ~100ms so the spinner clears quickly; after a server update, soft-nav must pick up the new `app.js` (cache-bust) and refresh **Open Creo models with** on the Creo pill so Modified / New files Open does not stay on a stale Windows-association path; if soft-nav **Loading…** cannot get HTML within ~45s (server busy on Open / index), fall back to a normal navigation instead of spinning forever | Hard-reload shell pages (SSR Session offline / drop Creo.JS); flash Session offline while Set Working Directory is visible; treat Logout / Login / setup as soft-nav; leave the connecting overlay up in a standalone browse; leave **Connecting to Creo…** up on the sign-in page after Logout; leave **Loading…** stuck forever when the server worker is blocked; trap clicks forever when Session stays offline; keep running an old in-memory `app.js` after deploy while only the HTML shell updates; leave Open mode stuck on association after Settings → Embedded because the live Creo pill was not refreshed; wait several seconds for agent `/health` before showing Connected when Creo.JS is already live |
| Sign in as **Viewer** | View products (`products.view`); open/download files and use **Details** (Overview/History) via the bottom toolbar or double-click (`objects.view`); Open without checking out (**no Open dialog** — only one choice) | See Add / Checkout / Check In / Remove / Export ▾ (including an empty **Checkout ▾** fly-up), New product, Copy to Vault, or “Check out … then open” in the Open dialog |
| Sign in with Administration only (no `products.view`) | Land on **Administration**; breadcrumb has no **Products** link; visiting `/` redirects to `/admin` | See a JSON error; see a Products crumb that opens Files |
| Sign in with a role that has **no permissions** | Land on a clear **No Files access** page (not JSON); product APIs stay **403** | Use the app as if signed in with Viewer |

| Wait while something big runs (Add, Remove, Check In…) | Show a busy message so you know it’s working | Sit frozen with no feedback |
| Press **Escape** on the busy overlay | For **cancellable** jobs only (**Rebuild Where Used**, **Collect metadata**, Utilities delete-and-rebuild Where Used): stop that job and clear the overlay. For other busy work (Add, Check In, Open, Compact…): keep the overlay up — do not abort mid-flight. If the overlay is closed while the app still thinks it is busy, clear the stuck state so the page is usable again | Show a redundant Cancel button on the busy overlay; dismiss Add/Check In/Open mid-flight and leave half-done work looking finished; leave a stuck modal / unclickable page after Escape |

**Name rules (new / rename)**

- Product name is required and must be **unique** (case-insensitive) across every product on the server — including Archived / inactive. Two products cannot share a name.
- Custom vault/workspace name: no spaces; or use the hash option instead.
- **Products** (Administration → Manage products; the page heading is **Products**) lists every product, has an **Add product** button, and shows **Created** (date/time) so you can tell products apart when cleaning up. Click a name to edit its name, number, and description. It does not copy a product or change lifecycle state.
- **Copy Products** opens a blank form (name, number, description, and initial comment are not filled in from the original). **Vault/Workspace name** is the same **Use hash** control as **New product**: the UUID is filled in and locked as soon as Copy opens (no hard refresh) until you uncheck it and type a folder name (no spaces, and not a vault folder another product already uses). Leave the comment blank to use the same History text as Add (**First check in: Add N files**). Copy creates a new product id and vault, then Adds the current vault files once: each file is **A.1**, **In Work**, and not checked out. Collected metadata and Where Used are copied onto those new A.1 rows. Git history on the copy is only the new product plus that Add. The original product is unchanged. Revision history, checkouts, product watches, and other people’s membership are not copied. Thumbnails stay stored by file bytes, so the original still has them (the copy shows them when the bytes match). The product name must be different from every existing product. Audit log records **Product copied** for the new product (summary names the source), not **Product created**.
- **Promote Products** changes one product at a time. Pick the product and the new lifecycle state, then confirm with your password. The Manage products tile is light yellow. The confirm window lists what that state **Allows** and **Blocks** using the same operations as **Manage products → Lifecycle states** (including what the change turns on or off compared with the current state). Role permissions still apply on top. That records **Product state changed**. Saving a name on Products stays **Product updated**.
- **Administration → Manage products → Baselines** (a Manage products tile, shown with `baselines.admin`, Administrator only by default; the permission appears under Roles → Baselines; it also makes the Manage products hub reachable): `/admin/baselines`. A row of counts (Baselines, Finalized, Archived, Release, Manual, Integrity warnings, Integrity errors), a **Search** box (baseline, product or creator), **Type** and **Status** filters and a table of **every baseline of every product** (Product, Baseline — a link to that product's Baselines tab, shown only to an account that can open products (otherwise plain text, because the Files page would send an admin-only account straight back to Administration) —, Type with its **R#** badge, Status, Members, Created, Created by, Integrity, Actions). There is **no Delete**: a baseline is immutable and pins the versions it holds. **Check** runs an integrity check of that baseline and opens the details; **Run integrity check** checks every baseline quickly. The check is read only and never repairs or substitutes anything: it verifies each member's object and version records, that the exact content is in the vault (and its size for Creo/PDF files), that the stored Git commit still exists, and the optional tag (Healthy / Warning / Error: missing or damaged content, a missing commit or missing records are **errors** and name the file and version; a moved, missing or uncreated tag is a **warning**; the stored commit stays the record). **Verify file hashes** in the details also reads every file through one `git cat-file --batch` and checks its SHA-256 (slower: a hash mismatch is `CORRUPT`). **Archive** opens the same confirmation window as the other administration actions (title “Archive baseline”, a short explanation of what happens, and **your password**; a browser alert is never used) and the server re-checks the password (`POST /api/baselines/{uuid}/archive` with `confirm_password`; a missing or wrong password changes nothing, and the permission is checked first). It deletes nothing: the baseline is **hidden from the product's Baselines tab and its count** (the “N Baselines” pill, the tab label) unless **Show archived** is ticked there (`?include_archived=true`; archived rows are muted with Status Archived), but it stays listed here (Status Archived), readable, comparable (the Compare list marks it “archived”) and downloadable by its uuid, keeps pinning its versions, still reserves its name, and **Restore** (a confirmation window that explains it, no password) returns it to Finalized; both are audited (“Baseline archived / restored”). API: `GET /api/admin/baselines`, `POST /api/admin/baselines/integrity`, `POST /api/baselines/{uuid}/integrity?deep=`, `POST /api/baselines/{uuid}/archive|restore` (all need `baselines.admin`). `/?product=<uuid>#baselines` opens a product's Baselines tab.
- **Releasing a product can create a release baseline.** When the new state is **Released** (and the product was not already Released), Promote Products shows a **Create a release baseline** box, **ticked by default**. Under it, **Also tag the repository** (ticked by default, shown only while the baseline box is ticked) creates the Git tag `release/R1`, `release/R2`, … on the release baseline's commit **after** the promotion commits: a tag problem (for example the name already exists) never undoes the release, the page says the tag could not be created, the baseline's `git_tag_status` is `FAILED` and **Retry tag** on the baseline's contents finishes it; the tag is never moved. Ticked, the promotion also records the product's next release **R1, R2, …** (`product_releases`) and a strict **Release** baseline named `<product>-R<n>` holding every file's exact Released version, in the same transaction: the files are marked Released first, then the baseline captures them as released (state Released in its members), then the release points at the baseline by id, so a release never depends on “latest”. The confirm window says so, and the page reports “Release R2 created with baseline Gearbox-R2”. The release baseline is strict (see Baselines → Release baseline): if a required dependency has no checked-in version, Where Used was never built for a product with assemblies or drawings, or released content is missing or damaged, the promotion is refused (“<product> cannot be released. …”) and **nothing** changes — state, files, release and baseline all roll back; untick the box to release without a baseline. A product with no checked-in files is released with a release record and no baseline. Releases are listed by `GET /api/products/{id}/releases` (needs `baselines.view`) and shown as an **R2** badge on the baseline; an old release is rebuilt by downloading its baseline. Promoting back and releasing again makes R2 and leaves R1 untouched; deleting the product deletes its releases and baselines. Without the box (and for the product API) no baseline is created.
- **Releasing a product releases its files.** When Promote Products moves a product to **Released**, every In-Work file in it becomes **Released** (Obsolete files stay Obsolete) in the same step, and the change is in the audit entry (“N files released”). Moving a product to **Released**, **In Review** or **Approved** while any file is **checked out** is **refused** with the file names and who holds them, because those states block Check Out and Undo/Force Undo follow the same matrix column, so the open checkout would be stranded — check the files in or undo the checkout first. Other states (Pre-Work, In Work, Under Change, Obsolete, Archived, Locked) are not refused for this reason. Moving the product back to an editable state (for example **Under Change**) does **not** make the files In Work again: a Released file only becomes editable through **Revise**. Existing Released products were updated once by migration `038`. **Undo a release:** when you promote a product that **has Released files** (it can be Released, Under Change, …) to **In Work** or **Pre-Work**, Promote Products shows an unchecked box **Also set the N Released files back to In Work (undo the release)** with a hint (not shown when the product has no Released files); ticked, the product's Released files become In Work again (the confirm says so, and the audit reads “N files set back to In Work”), and earlier Released revisions (A.x after a Revise) stay Released. Unchecked, the files stay Released and each needs a **Revise**. The box is not offered when moving to any other state (for example → Under Change); files already In Work are never touched.
- **Delete products**, **Compact product vault history**, and **Rebuild product database** on Manage products use a light red tile (password confirm). Products, Copy, and Product Membership stay white. **System Settings** (the Administration tile and every tile inside it, including Availability) is light red.
- The **Delete products** tip on Products (list and the edit form) appears only when the role can delete products. The page itself is **Manage products → Delete products** (not Utilities).

### Client script layout (`app.js` + lazy modules)

Testers do not see this, but it affects where regressions live. `app.js` is the shell (boot, selection, toolbar sync, busy overlay, soft-nav) and keeps **thin lazy wrappers** for heavy features. Classic scripts only — each module registers `window.__creopdmModules.<name>` with `init(shell)` and loads through `ensureModule("<name>")` from `/client/js/<name>.js`.

| Module | Owns | Loaded when |
|---|---|---|
| `admin.js` | Settings / Admin chrome | Admin / Settings pages |
| `modifications.js` | Ask AI check-in helper, History revert, Modifications (AI snapshot) tab | Details page / check-in Ask AI |
| `add.js` | Add dialog, pickers, drops, compressed import | Add menu, or `dragenter` (preload for page drop) |
| `metadata.js` | Collect job, Rebuild Where Used / Utilities rebuild, Where Used polling | Collect / Rebuild / Add index, or a stored Collect run / in-flight Where Used job |
| `creo_workspace.js` | Creo session gather/push metadata, agent materialize (per-file + zip), re-materialize after Check In | First Open / Collect / Check In workspace sync |
| `open.js` | Open chooser, checkout-before-open, prepare, File > Open trail, Windows association | First Open |
| `checkout.js` | Checkout selected / product, Undo Checkout, Force Undo Checkout | First Checkout / Undo / Force Undo |
| `checkin.js` | Check In / Add selected dialog, preview, submit, Ask AI row on the dialog | First Check In / Add selected |

`app.js` keeps the Files list, selection, `syncToolbar`, and metrics (too coupled for a `files.js` split). Quiet browse must **not** eager-load `checkout` / `checkin` / `open` / `add` / `metadata` / `creo_workspace` — only admin chrome and Details `modifications` load at boot when those pages are present.

Agent cache **listing / hash** helpers (`listAgentCacheFiles`, `hashAgentCachePaths`, `agentWorkdir`) stay in `app.js` because the Files list needs them on quiet boot (Modified / New local counts).

Test helpers: `tests/client_js.py` (`client_js_bundle()`); slice one function with `_between` from the module file that owns it (see `test_open_large_assembly_contract.py`, `test_ui_regressions.py`).

Mobile browse is CSS-only in `app.css`: `@media` with `pointer: coarse` and `hover: none` (plus width/height limits). Do **not** gate browse mode on `max-width` alone.

When you change any behavior above, update **this document** in the same change and add or adjust tests so the “must not” cases stay covered. See `.cursor/rules/user-interactions.mdc`.
